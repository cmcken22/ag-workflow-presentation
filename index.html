Terminology / important distinction

“Agentic workflow” here means GitHub Agentic Workflows.

When I say Agentic Agent, I mean an agent participating in a repeatable, repo-native workflow: explicit steps, handoffs, checks, and pull requests. The key distinction is how it is defined and triggered: this workflow is versioned in the repo and runs as GitHub Actions, including standard events such as an issue label being added.

This talk

GitHub Agentic Workflows

Agents are orchestrated as workflow steps, with concrete artifacts moving from plan to build to verify.

Not this talk

GitHub Cloud Agent

GitHub’s hosted coding agent that works on an issue or task in a cloud environment. It has a separate GitHub.com Automations surface with its own documented trigger list, not the versioned GitHub Actions workflow described here.

  • current triggers do not include issue labels
  • different product and execution model

“Agentic Agent” is shorthand here for one agent step inside a versioned GitHub Actions workflow.

Chapter 1

Getting the design to the agent.

Before the agent could build anything, it had to see the Figma file. That took three workarounds.

The starting point

One component. One agent. One run.

The target was a Bulk action bar: a real component with a selection count, actions, a divider, and a destructive action. The plan was to let a single GitHub Agent read the design, build it, and verify it.

  • one workflow run
  • one agent context
  • one final pull request
Problem 1 / access

The agent could not reach Figma.

The official Figma MCP signs in with OAuth in a browser. A GitHub Agent runs headless, with no browser and no session to reuse. Without the real design, it guessed.

Workaround 1

A proxy the agent can actually call.

The Figma REST API takes an API key, so it works without a browser. I wrapped its endpoints as MCP tools and put that proxy between the agent and Figma.

Problem 2 / design tokens

Structure came through. The design system did not.

The proxy could read files, walk nodes, and take screenshots. The variables endpoint is enterprise only, so every token binding came back as an ID with no value behind it.

A hard-coded token map.

I resolved a handful of variable IDs by hand and gave the proxy a lookup table. It proved the idea. Five tokens cannot describe a design system.

Chapter 2

Getting the agent to build well.

With the design in reach, the next problem was the agent itself.

A bigger target

From one component to a whole page.

The Correspondence landing page: tabs, search, a sortable table, pagination, and a filter drawer with a date range.

Problem 3 / the monolith

One massive agent file did everything.

Planning, coding, browser checks, and visual verification were packed into a single auto-build workflow. Every failure meant starting the whole run again.

One agent / one massive file

Auto-Build

Every job packed into a single run and a single context.

plancodebrowser checksvisual verify
Auto-Build Agent.md

The turning point

Three agents with explicit handoffs.

Each agent owns one kind of decision and hands off a concrete output. Commits make progress visible, and a failure restarts one station instead of the whole run.

Agent 1

Plan

Gathers the Figma source, maps it onto the component library, and writes the plan folder.

figma-plan.md
Agent 2

Build

Implements against the plan on a branch. Reads the plan and never edits it.

figma-build.md
Agent 3

Verify

Renders every state, scores it against the reference, then passes or sends feedback.

figma-verify.md
feedback until pass / max 8 rounds / 3% frame mismatch threshold
How the verifier sees it

Verification is a pixel-level measurement.

The Verify agent renders the built page, overlays it on the Figma reference, and marks every pixel that differs. That turns “it feels off” into a number and a place to look.

  • frame mismatch 4.27%
  • threshold for this run 1%
  • worst of 4 states 4.56%
  • result sent back to build
  • doubled text shows type that is offset or sized differently
  • solid outlines show borders the reference has and the build lacks, or the reverse
  • the same report feeds the builder’s next round
Problem 4 / the live MCP

Recognizably the page. But the MCP kept failing.

The three agents were still calling Figma live through the MCP during the run, and that was the weak link. When the context came back broken or cut short, the build filled the gaps.

  • MCP calls fail often
  • Figma API rate limited
  • token context too large, truncated
The fix / Figma harvest

Grab all the Figma context before the agent runs.

The harvest is a deterministic step. It pulls everything the agents need from Figma and writes it to disk before any agent starts. After that, we no longer need the Figma MCP at all.

Before / live Figma MCP

Ask Figma during the run.

  • calls fail often
  • Figma rate limits
  • token context too large, then truncated
Now / Figma harvest

Capture once, before the agents.

  • design tree, screenshots, tokens, and component inventory written to disk
  • deterministic: the same inputs every run
  • plan, build, and verify read files, with no Figma MCP
After the harvest

Almost perfect.

  • the icons are wrong: look at the sort arrows and the heart on the drawer button
  • some components are made up on the spot instead of taken from the library
Next / Figma Code Connect

code-connect.json maps each Figma component set to the React component that implements it. The builder picks the real icon and the real component instead of inventing one.

Chapter 3

Lessons learned.

Two things I would do from the start next time.

Lesson 1

Break the work into small, task-oriented agents. Then loop them.

One agent per task, with a clear handoff between them. Failures stay small, progress stays visible, and the loop keeps going until the result passes.

Plan
Build
Verify
not passing yet? back to build
Lesson 2

If something can be deterministic, make it deterministic.

The harvest replaced a live MCP that failed often with a step that produces the same files every time. Keep the agents for the parts that need judgment.
